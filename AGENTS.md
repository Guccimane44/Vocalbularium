# Working in Vocabularium

Preserve current product behavior. The current migration is repository foundation
work; do not split application modules, replace frameworks, redesign UI, normalize
storage, change authentication, or upgrade dependencies as incidental cleanup.

## Start here

- Read [the repository map](docs/agent-first/repository-map.md) for entry points,
  boundaries, commands, and document authority.
- Read [the behavior ledger](docs/agent-first/behavior-ledger.md) before changing
  product code. Known defects are tracked separately from preservation contracts.
- Use [versioned execution plans](docs/exec-plans/README.md) for migration work.
  Start the next eligible plan, record evidence, and keep incomplete gates visible.
- [The audit](docs/agent-first/audit.md) records the baseline and independent
  challenges. Its results are dated evidence, not a permanent green status.

## Current commands

From the repository root: `npm run setup`, `npm test`, `npm run typecheck`,
`npm run build`. Use Node 22.21.0/npm 10.9.4. `npm run doctor` checks prerequisites;
`npm run verify:fast` adds tooling/application tests, types and JS syntax;
`npm run verify` also builds/stages. See [development](docs/development.md).
Dependencies and lockfile live in `apps/web`. For local D1:
`npm --prefix apps/web run db:migrate`; then `npm run dev`.

Tests cover domain/auth/provider logic and simulated Chrome workers. Type checking
covers web TypeScript. Neither proves browser offline behavior or iOS compilation.
Lint exists at `npm --prefix apps/web run lint` and currently fails; do not suppress
its rules or run repository-wide formatting to manufacture a passing baseline.
Proposed commands in plans do not exist until their implementation is recorded.

## Boundaries and isolation

- Browser code intentionally imports `lib/domain.ts` for optimistic updates.
  Keep auth, persistence, provider credentials, and Worker runtime on the server.
- `Store.mutate` callbacks may replay: keep them synchronous and free of network
  effects. Preserve receipts, quota accounting, frozen attempts, and tombstones.
- Preserve the lockfile and append new database migrations; do not rewrite a
  migration already deployed. `dist` is generated by the root build.
- Use a dedicated checkout and disposable local state for destructive tests.
  Separate browser origins/profiles, Chrome profiles, and iOS simulators as needed.
  Worktrees still reference the same remote Site in both hosting manifests.
- Repository checks use local D1 and fixtures. Deployment, remote migrations,
  real providers, live account deletion, and access-policy changes are separate
  release work, outside this foundation migration.
- Keep tokens, `.env*`, `.dev.vars*`, database files, and user snapshots out of
  Git and test artifacts. `.dev.vars*` is ignored; fixture launchers also exclude active environment files.

## Finish a change

Run the checks appropriate to the touched boundary; report exact commands,
results, and limitations. Update the relevant plan and behavior evidence. Ask an
independent agent/reviewer to challenge significant migration changes. Record
disagreements and their disposition. A known failure needs an explicit owner and
follow-up; a skipped check is not a pass.
