# v0.3.0 local candidate — verification record

26 September 2026. The candidate targets `http://127.0.0.1:4318` with local PostgreSQL 18.6. It is separate from the historical Render/SQLite account and uses a fresh Chrome profile for that backend. The source revision, exact ZIP checksum and origin are recorded by `package-info.json` and the adjacent `.zip.sha256` file after packaging from a clean commit.

## Database and upgrade

- A disposable database with four populated prior-schema cards and their operation receipts was upgraded through the reviewed bounded-read migration. The resulting alphabetical orders matched JavaScript's Unicode normalization and code-unit comparison; all cards and receipt replay survived.
- The local development database (one seeded default deck, two layout pages, no cards at the time of backup) was backed up to private `.data/v0.3.0-development-20260926.dump` and restored to a separate database. Login, default-deck relationship, page count and card count were verified through the running API. The development database was not overwritten.
- A second rehearsal populated a disposable database with two cards and an edited Unicode front page, then used the same backup and restore commands into a separate database. Login, both cards, representative edited text, page relationships and replay of the original create operation passed. The synthetic databases were removed after verification.
- A separate disposable PostgreSQL 18 cluster on a random loopback port was stopped and restarted after saving a card. A new API process verified login, the same card identity, page relationship and text. Existing integration tests also cover API restart, ownership exclusion, bounded lock waits, database connection loss, preserved staged output and explicit recovery. Browser tests cover browser restart and abrupt process termination during generation. No physical machine reboot was performed.

## Extension update

Two disposable same-profile Chromium rehearsals used the same unpacked-extension folder and the same PostgreSQL-backed account. One started from the released 0.2.2 build at `b73ca22`; the other started from the WXT 0.2.2 build at `77e0fdd`. After replacing the files with 0.3.0, explicitly reloading the extension and reopening the profile, both preserved extension identity, signed-in access, Dark appearance, an existing card and a pending save. The pending save replayed once and its receipt cleared. Reopening without an explicit extension reload left the old service worker running, so the documented Reload step is required. This validates the same-backend update path; it does not migrate the separate hosted account into local PostgreSQL.

## Candidate checks and limits

The 0.3.0 source passed `npm run check`, 80 Node tests in `npm test`, and 18 Chromium scenarios in `npm run test:browser` on macOS with Chromium 151.0.7922.34. The temporary `allowJs` compiler option was removed; the dialog and sorting adapters shared by TypeScript views now have typed implementations. The extracted-package result and exact ZIP checksum are recorded with the candidate handoff. Native Windows PostgreSQL/browser acceptance and a physical machine reboot are not claimed. No live provider call or hosted deployment was performed for this local candidate.
