## Items

### 1. An Edit for the core

- **Before:** a parent card's core (meanings, translation or explanation) is edited only through the card's Edit, which opens every part. Each facet has its own Edit beside its heading.
- **After:** the core gets its own Edit, the same pencil and behaviour as a facet's. It sits at the end of the core's top line and shows on hover or focus, as a facet's actions do. It turns the core alone into an editor in place, with the toolbar and its own Save and Cancel. Save writes only the core's text over the content as the server has it, so facet edits made meanwhile elsewhere stay. The card's own Edit stays.
- **Not for:** a spoken core (Pronunciation), which has no text to edit, or a card that never generated.
- **Contract:** a component change can name the core, as it names a facet today. This is an amendment of D10 (a part's own Edit), with no new D-number.
- **Where:** `extension/card-content.tsx`, `page-view.tsx`, `pages.js`, `packages/contracts/src/pages.ts`, `src/core/store-pages.mjs` (`parentEdit`), and the [pages and editing](../specs/pages-and-editing.md#editing-one-facet) spec.
- **Accept:** a browser journey edits only the core and leaves the facets untouched, including a facet saved from a second installation meanwhile. Drafts, the leave warning and save recovery work as they do for a facet.

### 2. A back link on every view below home

- **Before:** only a page has a back link ("← My Deck"). The deck page, diagnostics, deck settings, a new deck and a new page have none; diagnostics has a "Back to decks" button among its actions.
- **After:** every view below home starts with the same back link as a page's, above its title, naming where it leads:

| View | Back link |
| --- | --- |
| Deck page | ← Home |
| Diagnostics | ← Home (the action-row button goes) |
| Deck settings | ← the deck |
| New deck | ← Home |
| New page | ← the deck |

- **Unsaved work:** leaving deck settings or a new page by the link asks first, as their Cancel does.
- **Where:** `dashboard.tsx`, `diagnostic-settings.js`, `configuration.tsx`, `page-view.tsx`, and locale strings in six languages.
- **Accept:** each view shows its link, and a browser journey follows each one. Arabic mirrors the arrow.

### 3. The deck card shows its module families (canvas)

- **Before:** a deck card on the home page shows its colour tab, name, page and module counts, the Default badge and ⋯.
- **After (A1, leaning row; owner, 5 November):** a little module card for each module family the deck's configuration uses (Languages, Expertise, Sound, Notes): paper, with the family's colour along its top edge and as a small index tab, and no symbol. The cards overlap in a row behind the deck card's top edge, the first in front, with only their tops showing at rest. On hover or focus the deck card lifts 4 px and the little cards rise to their own heights (6–14 px), leaning apart (−5° to +4°). Each starts 60 ms after the one before, with a strong spring (0.55 s). This is the hover motion of the 0.6.0 direction B (its sheets rising behind the card), which was never built. Under reduced motion they stand up without moving. They are named for screen readers (for example "Module families: Languages, Notes"). The deck's own colour stays on the card's top edge, and its separate colour tab goes.
- **Contract:** the deck summary gains the families its modules come from (read from `deck_modules`; no migration). The API changes and OpenAPI is regenerated.
- **Gate:** a canvas, together with items 4 and 6.

### 4. Deck actions as symbols, on the card and the deck page (canvas)

- **Before:** Set as default, Configure deck and Delete deck sit in the card's ⋯ menu.
- **After:** three icon buttons on the card: a star for Set as default (filled on the default deck), a gear for Configure deck, and a trash for Delete deck (with the existing confirmation). Each has a name and tooltip, a 24 px target, and keyboard focus.
- **The deck page too** (owner, 5 November): its head loses the ⋯ menu. The same three symbols, plus one for **Add page manually** (today's "+ Add page"), stand beside the deck's title, with the same names, tooltips and confirmation.
- **Gate:** the canvas proposes the symbols, where they sit on the card (always shown, or on hover and focus), how the default deck reads, and the deck page's head.

### 5. Reorder decks by dragging (D27)

- **Before:** decks keep their creation order (`decks.ordinal`).
- **After:** a deck drags into a new place by its body, with no grip of its own, with the pointer (a move beyond a few pixels, so a click still opens the deck) or with Space and the arrow keys. This works both as a card on the home page and as a row in the sidebar (owner, 5 November). Either move saves the order for the account, and the other list follows at once. The same drag library and motion as module reordering are used, and a failed save restores the order in both.
- **Decision D27:** decks keep a user-chosen order. A move is one idempotent mutation (`POST /api/deck/move`: deck, position), which renumbers `ordinal`. No migration is expected; the deck cursor already pages by `ordinal`.
- **Where:** `dashboard.tsx`, the sidebar (`shell.js`), `packages/contracts`, `src/core/store-decks.mjs`, `src/server/routes.mjs`.
- **Accept:** pointer and keyboard moves persist across a reload, from either list, and the other list shows the new order without a reload. A replayed operation ID returns its first result. Covered by `tests/server.test.mjs` / `tests/decks.test.mjs` and a browser journey.

### 6. Buttons with character (canvas)

- **Before:** buttons are plain outlined or ink rectangles: Add new deck, Cancel and Save in deck settings, the editors and dialogs, + Add page, Sign in.
- **After:** one button system in the Sage design: primary, secondary and quiet (ghost) buttons, with icons where they help (+ for add, a check for save). It defines size, radius, weight, hover, press and focus, light and dark. Placement is reconsidered too: Save and Cancel together at the end of an editor, primary actions in a page's head, and a sticky save bar in deck settings if it helps.
- **Gate:** the canvas shows every button in place, before and after.
- **Where:** `extension/app.css`, `extension/design/tokens.json`, and the views that place them.
- **Accept:** `npm run screens -- --base main` shows the changed buttons and no layout violations, and the contrast tests pass.
