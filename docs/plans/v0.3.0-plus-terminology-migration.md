# Terminology migration: deck → karte → seite

Recorded: 30 September 2026 (Europe/Berlin).

- [Notion plan — milestone 0.3.0+](https://app.notion.com/p/3eabb13502088136a7ddeceae08a092d)
- [Accepted terminology decision](https://app.notion.com/p/3eabb1350208813da027f7ea00548851)

## Goal and scope
Make **deck → karte → seite** the consistent vocabulary throughout the repository. Change names while preserving product behavior and existing data.
**Milestone:** 0.3.0+
**Implementation status:** In progress. Increment 1 establishes documentation and visible copy; increments 2 and 3 follow on separate review branches. See the [boundary inventory](../architecture/terminology-compatibility.md).
- Collection: **deck / decks**.
- Item within a deck: **karte / kartes**.
- Content surface within a karte: **seite / seites**.
Use English plurals, lowercase terms in prose, normal sentence capitalization in UI, and existing casing conventions in code.
Only pages within kartes—and their definitions in deck layouts—become seites. This migration does not introduce or propagate “view” or “webpage” terminology. Other meanings of “page” retain their existing terminology.

## 1. Inventory all affected terminology
Search documentation, extension code, backend code, shared packages, database definitions, tests, fixtures, scripts, prototypes, and generated references.
Classify each occurrence by meaning and whether it is persisted or externally consumed. Identify compatibility requirements before editing.
- card / cards → karte / kartes.
- card page / card pages → karte seite / karte seites.
- front page → front seite.
- card content page → karte content page.
- card view page → karte view page.
- deck configuration page → unchanged.
- page of query results → unchanged.
Use semantic replacements rather than replacing substrings. Words such as `discard` remain intact.

## 2. Establish the terminology in product documentation
Define the hierarchy in the product model:
> A deck contains kartes. Each karte contains one or more seites. The deck’s layout defines the seites and their configured modules.
Define a front seite, a deck-layout seite definition, and an individual karte’s seite content, preserving the distinction between generation configuration and saved content.
Propagate the vocabulary through `AGENTS.md`, README, product vision, scope, specifications, architecture, guides, plans, and the Change, Verify, and Deliver skills.
Rename relevant files, headings, and anchors—for example, `cards-and-editing.md` becomes `kartes-and-editing.md`. Update all incoming links in the same change.
Coordinate these edits with the specification taxonomy refactor already underway.

## 3. Update all product-facing language
Cover dashboard text, lists, editors, configuration controls, context menus, feedback, dialogs, errors, tooltips, and accessibility labels.
- “Create a card in ‘My Deck’” → “Create a karte in ‘My Deck’”.
- “Add card manually” → “Add karte manually”.
- “Open card” → “Open karte”.
- “Sort cards” → “Sort kartes”.
- “Number of pages” → “Number of seites”.
- “Page 2” → “Seite 2”.
- “Empty front page” → “Empty front seite”.
- “Retry this page” → “Retry this seite”.
Review singular/plural handling and sentence capitalization. Use kartes and seites, including in counts and descriptive prose.
Preserve saved user content, deck names, and generated text. This is a terminology migration of the application, not an edit to users’ material.

## 4. Rename internal code and supporting files
Update product-specific types, functions, variables, components, imports, filenames, CSS selectors, DOM attributes, test helpers, and comments.
Follow existing casing conventions:
- `CardRow` → `KarteRow`.
- `CardEditorDraft` → `KarteEditorDraft`.
- `DeckPageSchema` describing layout → `DeckSeiteSchema`.
- `cardId` → `karteId`.
- `pageId` describing a karte’s seite → `seiteId`.
- `basePageIds` → `baseSeiteIds`.
- `savePages()` saving seite content → `saveSeites()`.
- `card_id` / `page_id` → `karte_id` / `seite_id`.
Rename consumers together with declarations. Include maintained prototypes, smoke scripts, packaging helpers, and test filenames.
Inspect ambiguous names individually. A type representing a paginated batch must not become a seite.

## 5. Migrate API, messages, and navigation contracts
Update shared request/response schemas, HTTP routes, JSON fields, extension messages, domain error codes, and product-specific navigation identifiers.
Examples:
```text
/api/cards/:cardId       → /api/kartes/:karteId
/api/card/save           → /api/karte/save
cardId / pageId / pages  → karteId / seiteId / seites
```
Apply these field replacements only where their meanings match the product concepts. Preserve route structure and behavior rather than redesigning the API during the rename.
Update client and server together and regenerate OpenAPI.
Provide compatibility for previous extension builds, persisted requests, and existing navigation links. Define which legacy forms remain accepted and the conditions for removing that support.

## 6. Migrate database and persisted recovery state
Add a new database migration for relevant tables, columns, indexes, and constraints. Keep previously applied migrations intact.
Inspect persisted JSON and local state:
- Deck layouts and cached account objects.
- Operation receipts and stored results.
- Pending saves and capture receipts.
- Generation journals.
- Persisted drafts, where present.
Preserve IDs, relationships, content, timestamps, generation outcomes, and operation IDs.
Design replay compatibility explicitly. Existing operation fingerprints depend on operation names and payload fields; renaming those fields must not make an existing operation appear different, create duplicates, or discard pending work. Keep enough legacy representation to verify and replay old receipts correctly.

## 7. Verify terminology and upgrade behavior
Run the existing project checks, backend tests, browser tests, and build. Add focused migration coverage for:
- Fresh database creation and upgrade of a populated database.
- Pending operations created before the rename.
- Replaying an already committed operation after the rename.
- Retained generation journal results.
- Extension updates with recoverable local state.
- Legacy API and navigation compatibility.
Confirm that capture, manual editing, generation locks, destructive retry, interruption, and explicit save recovery retain their existing behavior.
Review visible copy, accessibility labels, documentation links, generated API references, and packaged output.

## 8. Audit remaining old terms and historical records
Search again for card, cards, page, and their identifier variants. Classify every remaining occurrence.
Legitimate remaining uses include unrelated meanings of page, compatibility adapters, historical migrations, and recorded evidence.
Preserve historical screenshots, raw test outputs, exact quotations, and release artifacts. Add a terminology mapping where needed so readers can connect historical language to current concepts. Active documentation and maintained implementation should consistently use the new terms.

## 9. Deliver in three reviewable increments
1. Update the canonical glossary, active documentation, and UI copy.
2. Rename internal implementation and supporting files, keeping legacy contract and storage names isolated at their boundaries.
3. Migrate contracts and persistence, add upgrade compatibility, and complete the repository-wide audit.
Each increment should remain runnable and reviewable.

## Completion criteria
- [ ] Current product language and implementation consistently use deck, karte, and seite.
- [ ] English plurals decks, kartes, and seites are used consistently.
- [ ] Existing data and pending operations survive upgrades without duplicates or loss.
- [ ] Required checks pass and results are recorded.
- [ ] Every retained old term has an explicit reason.
- [ ] No unrelated page terminology or product behavior is changed.
