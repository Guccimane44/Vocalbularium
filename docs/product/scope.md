# Current product scope

## Objective: What is supported now, and what is decided?

This document is the status ledger for product capabilities. It marks each capability with its status and links to the detailed behavior instead of repeating workflows. A requirement in a specification is never evidence that the capability exists; this ledger says whether it does. [Vision](vision.md) describes the longer-term direction; the [product model](model.md) defines the terminology. The [project workflow](../guides/project-workflow.md#from-decisions-to-iterations) describes how capabilities move through the statuses.

The current baseline is the Chrome extension with its local account backend. It supports collecting and consulting pages, with an initial set of language-oriented content modules. Broader possibilities in the vision are not automatically part of this scope.

The implemented capabilities below describe release 0.7.5. Release 0.4.0 implements the deck → page → component model approved in [Q72](../architecture/questionnaire/answers/answers-06-data-and-semantics.md#q72) through the [refactor plan](../history/plans/page-component-refactor.md) and [tracker #81](https://github.com/Guccimane44/Vocalbularium/issues/81). 0.4.1 adds capture with Context, and 0.5.0 adds page-owned modules and the module window ([D02](../architecture/traceability-map.md#entries)) and retires two modules ([D03](../architecture/traceability-map.md#entries)). 0.6.0 adds the Vocabularium Sage visual identity ([D05](../architecture/traceability-map.md#entries)). 0.6.1 fixes how modules make room while one is dragged in deck settings. 0.6.2 lets the user choose a deck's colour and shows an empty component as only its index tab ([D06](../architecture/traceability-map.md#entries)). 0.6.3 drags cards and modules by their label, turns the six dots into a menu, ejects a card's actions from its tab when clicked, and moves the deck-settings preview into a dialog ([D07](../architecture/traceability-map.md#entries)). 0.7.0 turns content modules into parent modules with a core and facets, German and Chinese, and retires the earlier three ([D08](../architecture/traceability-map.md#entries)). 0.7.1 shows a parent's facets as tags on its card and draws the modules in deck settings as empty cards. 0.7.2 places a facet added with its **+** by a ghost tag when several parents would take it, and numbers identical modules. 0.7.3 gives each facet its own **Retry**. 0.7.4 stores a parent's content as markdown per facet, formatted from the provider's JSON, and edits it with live formatting ([D09](../architecture/traceability-map.md#entries)). 0.7.5 edits without markdown, through a formatting toolbar, and lets a facet be edited on its own ([D10](../architecture/traceability-map.md#entries)). Builds up to v0.3.0+ used kartes and seites; [earlier terms](model.md#earlier-terms) maps the two.

## Status values

- `implemented`: shipped in the release named in *Since / target*, as the linked specification describes.
- `accepted for 1.0`: the owner accepted the decision record; the capability is specified but not built.
- `post-1.0`: accepted for a later version than 1.0.
- `out at maturity`: accepted as never part of the product.
- `deferred`: not yet classified. The *Decision* column names the record that is still `Proposed` or `Deferred`, or the plan that put the capability out of scope; "—" means no record covers it. The row moves to one of the statuses above when its record is accepted.

Release 0.7.5 implemented the editor without markdown, its formatting toolbar and a facet's own Edit ([D10](../architecture/traceability-map.md#entries), [plan](../plans/toolbar-editor.md)). Release 0.7.4 implemented the markdown parent content and live editor of [D09](../architecture/traceability-map.md#entries) ([plan](../plans/structured-content.md)). Release 0.7.0 implemented the parent modules of [D08](../architecture/traceability-map.md#entries) ([plan](../plans/parent-modules.md)). No capability is `post-1.0` or `out at maturity` yet: the questionnaire's decision records, including [Q04](../architecture/questionnaire/answers/answers-01-maturity-and-scope.md#q04)'s list of features excluded at maturity, are still `Proposed`. The [traceability map](../architecture/traceability-map.md) tracks how each answer reaches the specifications.

## Upgrade from earlier builds

Upgrading to 0.4.0 discards every deck and karte created by earlier builds. Accounts and sign-in stay, and the account starts again with one fresh My Deck. Extensions older than 0.4.0 do not work with the 0.4.0 backend.

Upgrading from 0.4.0 to 0.4.1 keeps all decks and pages. Migration `0005` adds the deck setting **Capture with Context**, on for every existing deck. Upgrade the backend and the extension together: a 0.4.1 extension saving deck settings needs the 0.4.1 backend.

Upgrading to 0.5.0 discards every deck and page again, as 0.4.0 did, because the earlier data was for testing ([D02](../architecture/traceability-map.md#entries)). Accounts and sign-in stay, and the account starts again with one fresh My Deck holding the main key, Context, and `German explanation + examples` modules. On the way, migration `0006` retires `<The selected>` and `<The selected + original language tag>` ([D03](../architecture/traceability-map.md#entries)): it removes their instances and components, which matters only for a database that stops at `0006`. Migration `0008` then discards decks and pages. Upgrade the backend and the extension together: the 0.5.0 extension's first start clears cached content, unsent captures and pending saves from earlier builds and keeps sign-in, and older extensions do not work with the 0.5.0 backend.

Upgrading from 0.5.0 to 0.5.1 keeps all decks and pages; there is no migration. Restart the API with 0.5.1 and reload the extension: per-card **Generate** relies on the 0.5.1 backend starting a never-generated, empty component without confirmation (an older backend would ask first).

Upgrading from 0.5.1 to 0.5.2 keeps all decks and pages; there is no migration and no API change. Reload the extension; restarting the API only updates its reported version.

Upgrading from 0.5.2 to 0.6.0 keeps all decks and pages; there is no migration. Restart the API with 0.6.0, then reload the extension: the page list's meaning line and family marks come from fields the 0.6.0 API adds to page summaries. A 0.5.2 extension ignores those fields and keeps working with the 0.6.0 API; a 0.6.0 extension with a 0.5.2 API shows its page lists without meanings or marks. Appearance now follows the system setting until it is chosen in the account menu, so a 0.5.2 Light or Dark choice is kept as that choice.

Upgrading from 0.6.0 to 0.6.1 keeps all decks and pages; there is no migration and no API change. Reload the extension; restarting the API only updates its reported version.

Upgrading from 0.6.1 to 0.6.2 keeps all decks and pages. Stop the API, run `npm run db:migrate` (migration 0009 adds an empty deck colour, so every deck keeps the colour it showed), start the API with 0.6.2, then reload the extension. Deck reads and deck summaries gain a `colour` field, and a deck save accepts one. A 0.6.1 extension ignores the field and keeps working with the 0.6.2 API; a 0.6.2 extension cannot save a deck through a 0.6.1 API, which rejects the field.

Upgrading from 0.6.2 to 0.6.3 keeps all decks and pages; there is no migration. Restart the API with 0.6.3, then reload the extension: the 0.6.3 API retries a component with nothing in it (one that failed or generated nothing) without asking for confirmation, as the 0.6.3 extension expects. With a 0.6.2 API such a retry falls back to the confirmation dialog.

Upgrading from 0.6.3 to 0.7.0 discards every deck and page again, because the earlier data was for testing ([D08](../architecture/traceability-map.md#entries)). Accounts and sign-in stay, and the account starts again with one My Deck holding the main key, Context, and `German` with Article, Examples, Synonyms and Antonyms. Stop the API, back up with `npm run db:backup`, run `npm run db:migrate` (migration `0010` adds facet lists and run order; `0011` discards the decks and pages and retires `German explanation`, `German explanation + examples` and `Sentence usage`), start the API with 0.7.0, then reload the extension. Finish or discard pending saves before upgrading: a save for a discarded page fails as deleted. Upgrade the backend and the extension together: a 0.6.3 extension cannot add or render the parent modules, and the 0.7.0 extension needs the 0.7.0 API's facet routes, facet lists and interpretation.

Upgrading from 0.7.0 to 0.7.1 keeps every deck and page: 0.7.1 changes only the extension's interface, and the API gains no migration or route. Stop the API, start it with 0.7.1 so that it reports the same version, then replace the extension's files and reload it.

Upgrading from 0.7.1 to 0.7.2 is the same: every deck and page stays, there is no migration or new route, and only the extension's interface changes. Stop the API, start it with 0.7.2, then replace the extension's files and reload it.

Upgrading from 0.7.2 to 0.7.3 keeps every deck and page and needs no migration. The API's generate route accepts a facet target, so the API and the extension must both be 0.7.3: stop the API, start it with 0.7.3, then replace the extension's files and reload it.

Upgrading from 0.7.3 to 0.7.4 discards every deck and page again, because a parent's content changes from markup text to markdown per facet with a structured top line ([D09](../architecture/traceability-map.md#entries)). Accounts and sign-in stay, and the account starts again with one My Deck. Stop the API, back up with `npm run db:backup`, run `npm run db:migrate` (migration `0012` discards the decks and pages and starts structured content; `0013` discards them again and stores each parent's core and facets as markdown), start the API with 0.7.4, then reload the extension. Finish or discard pending saves before upgrading: a save for a discarded page fails as deleted. Upgrade the backend and the extension together: a 0.7.3 extension cannot render or edit the 0.7.4 content, and the 0.7.4 extension needs the 0.7.4 API's parent saves.

Upgrading from 0.7.4 to 0.7.5 keeps every deck and page. A one-time migration converts content so it reads as before: the main key's automatic emphasis becomes stored highlights in parent content and in Context, and Context and Text become markdown with their characters kept as typed. A save can now name the one facet it changes, which the 0.7.5 API applies over the content it has stored, so the API and the extension must both be 0.7.5: stop the API, start it with 0.7.5, then replace the extension's files and reload it. A 0.7.4 API would save the whole component instead.

## Current delivery boundary

The product is an owner-test Chrome extension delivered through manual installation, with a local backend and persistent PostgreSQL storage. Real model generation requires an external provider. The [local development guide](../architecture/local-postgresql.md) describes the current environment and operating constraints.

The earlier hosted MVP is a separate historical environment. Current scope does not establish public-release readiness or claim that every platform and recovery scenario has been verified. Acceptance and verification evidence belong in release records.
