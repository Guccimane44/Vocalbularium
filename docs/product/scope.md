# Current product scope

## Objective: What is supported now, and what is decided?

Vocabularium is an owner-test Chrome extension with a local account backend. It captures words, phrases and sentences into decks of pages, and builds each page from modules: German and Chinese translations with their facets, the Expertise modules Computer Science and Mathematics, and Pronunciation, spoken by ElevenLabs. The interface is localised into six languages. The [capability ledger](#capability-ledger) lists what is implemented, with the release that shipped it, and what is still deferred.

This document is the status ledger for product capabilities. It marks each capability with its status and links to the detailed behavior instead of repeating workflows. A requirement in a specification is never evidence that the capability exists; this ledger says whether it does. [Vision](vision.md) describes the longer-term direction; the [product model](model.md) defines the terminology, and [earlier terms](model.md#earlier-terms) maps the vocabulary of builds up to v0.3.0+. The [project workflow](../guides/project-workflow.md#from-decisions-to-iterations) describes how capabilities move through the statuses, and the [traceability map](../architecture/traceability-map.md) how each decision reaches the specifications.

## Status values

- `implemented`: shipped in the release named in *Since / target*, as the linked specification describes.
- `accepted for 1.0`: the owner accepted the decision record; the capability is specified but not built.
- `post-1.0`: accepted for a later version than 1.0.
- `out at maturity`: accepted as never part of the product.
- `deferred`: not yet classified. The *Decision* column names the record that is still `Proposed` or `Deferred`, or the plan that put the capability out of scope; "—" means no record covers it. The row moves to one of the statuses above when its record is accepted.

No capability is `post-1.0` or `out at maturity` yet: the questionnaire's decision records, including [Q04](../architecture/questionnaire/answers/answers-01-maturity-and-scope.md#q04)'s list of features excluded at maturity, are still `Proposed`.

## Upgrade from earlier builds

Each release's upgrade path, oldest first. An upgrade keeps accounts and sign-in; the notes say when decks and pages are discarded.

Upgrading to 0.4.0 discards every deck and karte created by earlier builds. Accounts and sign-in stay, and the account starts again with one fresh My Deck. Extensions older than 0.4.0 do not work with the 0.4.0 backend.

Upgrading from 0.4.0 to 0.4.1 keeps all decks and pages. Migration `0005` adds the deck setting **Capture with Context**, on for every existing deck. Upgrade the backend and the extension together: a 0.4.1 extension saving deck settings needs the 0.4.1 backend.

Upgrading to 0.5.0 discards every deck and page again, as 0.4.0 did, because the earlier data was for testing ([D02](../architecture/decisions/d02.md)). Accounts and sign-in stay, and the account starts again with one fresh My Deck holding the main key, Context, and `German explanation + examples` modules. On the way, migration `0006` retires `<The selected>` and `<The selected + original language tag>` ([D03](../architecture/decisions/d03.md)): it removes their instances and components, which matters only for a database that stops at `0006`. Migration `0008` then discards decks and pages. Upgrade the backend and the extension together: the 0.5.0 extension's first start clears cached content, unsent captures and pending saves from earlier builds and keeps sign-in, and older extensions do not work with the 0.5.0 backend.

Upgrading from 0.5.0 to 0.5.1 keeps all decks and pages; there is no migration. Restart the API with 0.5.1 and reload the extension: per-card **Generate** relies on the 0.5.1 backend starting a never-generated, empty component without confirmation (an older backend would ask first).

Upgrading from 0.5.1 to 0.5.2 keeps all decks and pages; there is no migration and no API change. Reload the extension; restarting the API only updates its reported version.

Upgrading from 0.5.2 to 0.6.0 keeps all decks and pages; there is no migration. Restart the API with 0.6.0, then reload the extension: the page list's meaning line and family marks come from fields the 0.6.0 API adds to page summaries. A 0.5.2 extension ignores those fields and keeps working with the 0.6.0 API; a 0.6.0 extension with a 0.5.2 API shows its page lists without meanings or marks. Appearance now follows the system setting until it is chosen in the account menu, so a 0.5.2 Light or Dark choice is kept as that choice.

Upgrading from 0.6.0 to 0.6.1 keeps all decks and pages; there is no migration and no API change. Reload the extension; restarting the API only updates its reported version.

Upgrading from 0.6.1 to 0.6.2 keeps all decks and pages. Stop the API, run `npm run db:migrate` (migration 0009 adds an empty deck colour, so every deck keeps the colour it showed), start the API with 0.6.2, then reload the extension. Deck reads and deck summaries gain a `colour` field, and a deck save accepts one. A 0.6.1 extension ignores the field and keeps working with the 0.6.2 API; a 0.6.2 extension cannot save a deck through a 0.6.1 API, which rejects the field.

Upgrading from 0.6.2 to 0.6.3 keeps all decks and pages; there is no migration. Restart the API with 0.6.3, then reload the extension: the 0.6.3 API retries a component with nothing in it (one that failed or generated nothing) without asking for confirmation, as the 0.6.3 extension expects. With a 0.6.2 API such a retry falls back to the confirmation dialog.

Upgrading from 0.6.3 to 0.7.0 discards every deck and page again, because the earlier data was for testing ([D08](../architecture/decisions/d08.md)). Accounts and sign-in stay, and the account starts again with one My Deck holding the main key, Context, and `German` with Article, Examples, Synonyms and Antonyms. Stop the API, back up with `npm run db:backup -- .data/backup-before-0.7.0.dump` (it needs a file it has not written before), run `npm run db:migrate` (migration `0010` adds facet lists and run order; `0011` discards the decks and pages and retires `German explanation`, `German explanation + examples` and `Sentence usage`), start the API with 0.7.0, then reload the extension. Finish or discard pending saves before upgrading: a save for a discarded page fails as deleted. Upgrade the backend and the extension together: a 0.6.3 extension cannot add or render the parent modules, and the 0.7.0 extension needs the 0.7.0 API's facet routes, facet lists and interpretation.

Upgrading from 0.7.0 to 0.7.1 keeps every deck and page: 0.7.1 changes only the extension's interface, and the API gains no migration or route. Stop the API, start it with 0.7.1 so that it reports the same version, then replace the extension's files and reload it.

Upgrading from 0.7.1 to 0.7.2 is the same: every deck and page stays, there is no migration or new route, and only the extension's interface changes. Stop the API, start it with 0.7.2, then replace the extension's files and reload it.

Upgrading from 0.7.2 to 0.7.3 keeps every deck and page and needs no migration. The API's generate route accepts a facet target, so the API and the extension must both be 0.7.3: stop the API, start it with 0.7.3, then replace the extension's files and reload it.

Upgrading from 0.7.3 to 0.7.4 discards every deck and page again, because a parent's content changes from markup text to markdown per facet with a structured top line ([D09](../architecture/decisions/d09.md)). Accounts and sign-in stay, and the account starts again with one My Deck. Stop the API, back up with `npm run db:backup -- .data/backup-before-0.7.4.dump` (it needs a file it has not written before), run `npm run db:migrate` (migration `0012` discards the decks and pages and starts structured content; `0013` discards them again and stores each parent's core and facets as markdown), start the API with 0.7.4, then reload the extension. Finish or discard pending saves before upgrading: a save for a discarded page fails as deleted. Upgrade the backend and the extension together: a 0.7.3 extension cannot render or edit the 0.7.4 content, and the 0.7.4 extension needs the 0.7.4 API's parent saves.

Upgrading from 0.7.4 to 0.7.5 keeps every deck and page. A one-time migration converts content so it reads as before: the main key's automatic emphasis becomes stored highlights in parent content and in Context, and Context and Text become markdown with their characters kept as typed. A save can now name the one facet it changes, which the 0.7.5 API applies over the content it has stored, so the API and the extension must both be 0.7.5: stop the API, start it with 0.7.5, then replace the extension's files and reload it. A 0.7.4 API would save the whole component instead.

Upgrading from 0.7.5 to 0.8.0 keeps every deck and page. Migration `0015` adds an empty generation record to every component, so components generated before 0.8.0 have none; stored content does not change. The Translation family is now called Languages, and the module window adds the Expertise family with `Computer Science` and `Mathematics`. Stop the API, back up with `npm run db:backup -- .data/backup-before-0.8.0.dump` (it needs a file it has not written before), run `npm run db:migrate`, start the API with 0.8.0, then replace the extension's files and reload it. Upgrade the API and the extension together: only 0.8.0 builds know the Expertise modules.

Upgrading from 0.8.0 to 0.8.1 keeps every deck and page; there is no migration and no API change. Replace the extension's files and reload it; restarting the API only updates its reported version. Facets are now chosen in a parent's facet window, from **Facet** among its actions, instead of the module window ([D13](../architecture/decisions/d13.md)).

Upgrading from 0.8.1 to 0.9.0 keeps every deck and page. Migration `0016` adds the account's interface language, English, so the interface looks as before until another language is chosen under **Account → Language** ([D14](../architecture/decisions/d14.md)). Stop the API, back up with `npm run db:backup -- .data/backup-before-0.9.0.dump` (it needs a file it has not written before), run `npm run db:migrate`, start the API with 0.9.0, then replace the extension's files and reload it. The API gains `POST /api/language`, and the account summary a `language` field; a 0.8.1 extension ignores it and keeps working in English with the 0.9.0 API, while a 0.9.0 extension with a 0.8.1 API cannot save a language. Once a language other than English is chosen, the Expertise modules write in it.

Upgrading from 0.9.0 to 0.9.1 keeps every deck and page; there is no migration and no API change. Replace the extension's files and reload it; restarting the API only updates its reported version.

Upgrading from 0.9.1 to 0.10.0 keeps every deck and page; there is no migration and no API change. Restart the API with 0.10.0, then replace the extension's files and reload it. From then on the Expertise modules write with the writing guide of the interface language, and a reply that lacks only the brace closing its core is repaired rather than failed; components generated earlier keep their content and prompt version until regenerated. A language is offered once its strings, its writing guide and its Expertise output are reviewed, which all six are.

Upgrading from 0.10.0 to 0.11.0 keeps every deck and page; there is no migration and no API change. Restart the API with 0.11.0, then replace the extension's files and reload it. From then on the Computer Science and Mathematics modules give one plain sentence for a key outside their subject, explain a technical term of a neighbouring field in one paragraph, and no longer explain an everyday meaning or the Context unless a Context uses an outside sense; components generated earlier keep their content and prompt version until regenerated.

Upgrading from 0.11.0 to 0.12.0 discards every deck and page again, because the earlier data was for testing and development ([D17](../architecture/decisions/d17.md), K49). Accounts, sign-in and the language preference stay, and the account starts again with one My Deck holding the main key, Context, and `German` with Article, Examples, Synonyms and Antonyms. Stop the API, back up with `npm run db:backup -- .data/backup-before-0.12.0.dump` (a file it has not written before), run `npm run db:migrate` (migration `0017` discards decks, pages, runs, attempts and receipts and drops the run's stored interpretation), start the API with 0.12.0, then replace the extension's files and reload it: its first start clears cached content, unsent captures and pending saves from earlier builds and keeps sign-in. Finish or discard pending saves before upgrading: a save for a discarded page fails as deleted. Upgrade the backend and the extension together: a 0.11.0 extension expects the run's interpretation, and the 0.12.0 extension needs the cards' own top lines.

Upgrading from 0.12.0 to 0.12.1 keeps every deck and page; there is no migration and no API change. Replace the extension's files and reload it; restarting the API only updates its reported version.

Upgrading from 0.12.1 to 0.12.2 keeps every deck and page; there is no migration. Restart the API with 0.12.2 (a card's Retry now sends its saved core), then replace the extension's files and reload it. An attempt started under 0.12.1 finishes as it began.

Upgrading from 0.12.2 to 0.13.0 keeps every deck and page; there is no migration. Restart the API with 0.13.0, then replace the extension's files and reload it. The explanations become family, module and facet pages, with samples in the interface language.

Upgrading from 0.13.0 to 0.13.1 keeps every deck and page; there is no migration. Restart the API with 0.13.1 (Computer Science's facet now writes Python), then replace the extension's files and reload it. A card's existing Code example keeps its code and shows as Python.

Upgrading from 0.13.1 to 0.13.2 keeps every deck and page; there is no migration and no API change. Restart the API with 0.13.2 (a card's Retry after a changed main key reads the new key), then replace the extension's files and reload it.

## Current delivery boundary


The product is an owner-test Chrome extension delivered through manual installation, with a local backend and persistent PostgreSQL storage. Real model generation requires an external provider. The [local development guide](../architecture/local-postgresql.md) describes the current environment and operating constraints.

The earlier hosted MVP is a separate historical environment. Current scope does not establish public-release readiness or claim that every platform and recovery scenario has been verified. Acceptance and verification evidence belong in release records.
