# D25: facets owned by their module

**Opened:** 2026-10-31. **Source:** the owner's 0.15.0 cleanup plan ([plan](../../plans/cleanup-and-refinement.md#c-facets-owned-by-their-module), approved 31 October 2026), ahead of the language expansion, in which each language gets the facets its dictionary can offer. **Accepted:** by the owner in chat on 31 October 2026 ("Accept both"). **Notion:** [decision record](https://app.notion.com/p/40abb1350208819fbc89c3924da4c957).

## Decision

- A parent's stored `facets` is keyed by facet ID (`^[a-z][a-z0-9-]{0,39}$`, at most twelve, each markdown up to 8,000 characters). The contract names no facet; the module catalog alone decides which facets a module has, and the domain rejects a facet its module lacks.
- My Deck and a new deck's draft take their modules from the catalog (`DEFAULT_DECK_MODULES`, `packages/domain/src/catalog/index.ts`); German names the facets it brings to a new deck.
- A module's names in the interface languages other than English live beside it (`names.<language>.json`), and the samples' words beside the module or facet that uses them (`sample-keys.json`, `sample-key.json`). Tests and scripts take a family's modules from the catalog (`parentsIn`).
- The card header keeps `romanization` and `gramRole`, which suit most languages; a language-specific header field is decided with the language that needs it.

No stored data changes and no migration; the OpenAPI schema loosens.
