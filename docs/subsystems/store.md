# Store

The store is the API's one way into the account's data in PostgreSQL 18: decks and their configuration, pages and their components, generation runs and attempts, audio clips, reports, sign-in and operation receipts. It runs every mutation once, in arrival order, inside a transaction. How a client gets a change to it is in [capture and save](capture-and-save.md); what generation writes is in [generation](generation.md). Starting a local database, keeping it apart from an old installation, and backing it up are in the [local PostgreSQL guide](../guides/local-postgresql.md).

## Runtime path

1. A request reaches its route in [`routes.mjs`](../../src/server/routes.mjs). Fastify checks it against its TypeBox contract; a mismatch is rejected before the store sees it.
2. The route calls the store. A mutation goes through `command`: the ordered executor admits it in arrival order, a transaction opens with the account row lock, the receipt is looked up, and either the first result is replayed or the change runs and its receipt is written in the same transaction.
3. A failure throws `StoreError` with a code (`invalid`, `deleted`, `stale_session`, `generating`, `confirmation_required`, `operation_reused`, …); the transaction rolls back, so nothing is half-written.
4. The commit happens before the reply. A route that starts work outside the database (generation, audio) does so only after the commit, and only for a first acceptance, never a replay.

## Behaviour

### Default deck

Every account has exactly one default deck, the destination for capture. Default is a role a deck holds, not a kind of deck. A new account starts with **My Deck** as its default deck, created once when the account is initialized. Its initial configuration is defined in [capture and generation](#initial-default-deck-example). **Set as default** moves the role to another deck; the choice synchronizes with the account.

### Initial default-deck example

The initial **My Deck** has the main key module, the Context module, and one content module instance: `German`, with Article, Examples, Synonyms and Antonyms. A new deck starts with the same configuration. German's other facets are not in it.

For the selected input `幸福`, read as a word, the page shows its main key `幸福`, then a `German` component, whose header names the key's language, that it is a word and its grammatical role: an explanation in German of the word, then the article of its German translation (`das Glück`), examples with their translations, synonyms, and antonyms, following the [modules specification](module-catalog.md#catalog). The exact generated wording may vary.

For a selected sentence such as `我真的很幸福`, the `German` component shows the German translation and, from Examples, one similar sentence with its translation; Article, Synonyms, and Antonyms do not apply to a sentence and are not shown. This is an intentional, successfully completed page.

### Configuration and pages

The configuration is the template for page creation. Capture and manual creation give the new page a copy of the deck's content module instances, in configured order ([capture and save](capture-and-save.md#what-a-capture-saves)). From then on the page owns its modules:

- Saving a configuration change never changes existing pages. Only pages created afterwards use it.
- Generation and retry on an existing page use the page's own module instances, not the deck's.
- A page moved to another deck keeps its modules and components.

A generation run already in progress when the configuration changes is unaffected.

### Page summaries and layouts

Every page is shown through the default view. Choosing among several views per deck, switching views, and configuring other view modules (such as the card view module) are later work. When they arrive, they follow the [Notion-style model](../product/model.md#view): a view shows one page, with one default per deck.

How a deck **lists** its pages is a separate choice, its page list **layout**: List (the default), Table, or Gallery ([deck](../screens/deck.md)). The layout is remembered per deck on each installation and is not part of the deck configuration. To fill every layout without loading each page, a page summary from the backend (the deck's page list and the recent captures) carries, besides the main key, capture date and page status, the page's meaning line and, for each component after the main key, its module type, status, and whether it has content. It never carries the content itself.


## Constraints and failure behaviour

- **Applied migrations never change.** A schema change is a new migration made with `npm run db:generate`. Nothing checks this; a reviewer does.
- **Upgrades keep accounts and sign-in**, and keep decks and pages unless the owner decides otherwise; each release says what its upgrade keeps in its [release notes](../releases/README.md).
- **No generated content is cached**, audio included: the store keeps what a card holds, never a reusable answer.

### Ordering, recovery, and single-process ownership

The persistence boundary has an explicit owner account ID. Only account `1` is supported; this is not multi-tenant authorization. Complete validated commands are admitted to the per-account executor before asynchronous handler authentication. Initial authentication also runs in that executor. Each mutation commits with its operation receipt before acknowledgment. Replaying an operation returns the original result and sequence; a different payload with the same operation ID is rejected.

All account mutations, authentication writes, generation transitions, and assembled reads use the same ordered executor. Transactions acquire the account row lock and use repeatable-read isolation, so a snapshot cannot combine different deck configuration or page revisions. Query, lock, connection, and idle-transaction waits are bounded. Provider calls run outside the executor and transactions. A save rejected while a component is generating is not queued for eventual application; the user must resubmit explicitly under the existing [recovery rules](capture-and-save.md#saving-every-change).

One dedicated pool connection holds an advisory ownership lock. A second API or a migration attempt against an active API fails. This enforces the one-process deployment limit; database locks alone are not used to claim cross-process arrival ordering. The pool holds at most five connections including ownership. If ownership is lost, readiness fails and account operations stop until the API restarts; liveness still responds.

Completed provider results that cannot reach PostgreSQL are retained in memory and in `DATA_DIR/generation-outbox`. Keep that directory on durable storage alongside database backups. Startup stages retained journal results without calling the provider again; unfinished attempts without a staged/journaled result fail. Publication still requires the originating browser session. No automatic provider retry or failed-save resubmission is introduced. If both the journal and database writes fail before a process exit, unstored output cannot be recovered; a retry remains necessary. PostgreSQL does not make the filesystem journal durable by itself.

## Verification

### Commands and disposable databases

```sh
npm run check
npm test
npx playwright install chromium
npm run test:browser
npm run build
python3 scripts/package.py
```

Tests load `.env.postgres` when present. CI supplies `TEST_DATABASE_ADMIN_URL` directly. It must address the loopback `postgres` maintenance database, never `vocabularium_dev`. Each fixture creates a random `vocabularium_test_<24 hex characters>` database, applies migrations, and drops only its own generated name during cleanup. Cleanup closes the fixture's connections, then uses plain `DROP DATABASE`, which stops autovacuum workers itself and waits briefly for closing sessions. It retries with `WITH (FORCE)` only when a session still holds the database (`55006`). FORCE is not the first attempt because it needs `pg_signal_backend` to terminate an autovacuum worker; without that role it fails with `permission denied to terminate process` (`42501`) whenever autovacuum is analyzing the freshly migrated database. The test role needs no `pg_signal_backend` membership, and CI runs without it. A process killed outside test cleanup can leave disposable databases for manual inspection; there is no broad prefix-based reset command. Tests do not require local Docker and inject controlled generation providers.

Browser tests own ports 4317/4318 and temporary Chrome profiles. Check for listener conflicts before running them.

GitHub Actions runs database/browser suites on Linux with PostgreSQL 18. Ubuntu and Windows retain syntax, strict type checks, extension-worker checks, building, and packaging. Native Windows PostgreSQL/browser coverage is not claimed.
