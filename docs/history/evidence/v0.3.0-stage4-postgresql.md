# v0.3.0 Stage 4 — PostgreSQL verification

Recorded 23 September 2026 on `codex/v0.3.0-postgresql`, based on Stage 3 commit `a124742`. Tracking: [issue #48](https://github.com/Guccimane44/Vocalbularium/issues/48). This is an architecture-stage verification record, not final v0.3.0 owner acceptance or a hosted deployment.

## Environment and scope

- Apple Silicon macOS, Node 24.21.0, npm 11.19.0, Homebrew PostgreSQL 18.6.
- Local cluster inspected before starting: shut down, no 5432 listener, only the maintenance database/user present. Started on `127.0.0.1` without changing its persistent configuration or enabling a boot service.
- Dedicated development database with separate non-superuser application, migration, and disposable-test roles. Verified the application role cannot create schema objects. Generated connection settings remain in ignored `.env.postgres`, mode `0600`; no credentials are recorded here.
- All automated generation used controlled providers. The test helper supplies a controlled failing provider by default, regardless of ambient provider credentials.
- Existing SQLite files, prior Chrome profiles, and hosted account preserved. No imported vocabulary, paid provider request, Render deployment, merge, release tag, or version bump.

## Automated checks

- Clean `npm ci`: passed; audit reported zero vulnerabilities. A scoped esbuild override removes the migration tool's vulnerable development-only transitive version.
- `npm run check`: syntax, JSON, whitespace, and strict TypeScript checks passed.
- `npm test`: **66 passed**, including **11** PostgreSQL concurrency, recovery, migration, and reset-safety regressions.
- `npm run test:browser`: **17 passed**, Chromium 151.0.7922.34. Includes lost acknowledgments, worker suspension, abrupt browser termination, two-installation generation locks, authentication-loss draft retention, feedback timing, themes, navigation, and explicit recovery. No scenario was removed.
- `npm run build` and `python3 scripts/package.py`: passed for `http://127.0.0.1:4318`, including archive integrity validation. The package remains version **0.2.2** until the planned v0.3.0 release-candidate stage. This ZIP is build evidence, not the release handoff; extracted-artifact acceptance remains Stage 7.
- `npm run db:generate`: no schema drift after applying the committed Drizzle migration.
- `npm run openapi`: passed without a database; the existing HTTP contract reference did not change.
- `git diff --check`: passed.

The additional PostgreSQL regressions cover concurrent duplicate and mismatched operation IDs, admission order, same/different-page saves, atomic generation-lock rejection, layout removal versus publication, deletion, session invalidation, rollback after earlier writes, migration reapplication, startup recovery, rejection of a second API/migration owner, bounded lock waits, actual connection termination, journal recovery without another provider call, and refusal to reset the development database. Synchronization points use committed state/promises rather than sleeps to establish correctness.

The ownership-loss regression initially exposed delayed observation of connection termination. The persistence boundary now verifies the owning connection before a transaction and before commit. The regression passes, and liveness remains available when readiness fails.

## Local operations

`npm run db:setup` succeeded twice and preserved the seeded development account. Development startup created one empty **My Deck** with its two original pages using the restricted application role.

With `PG_BIN` set to the installed PostgreSQL 18 tools, `npm run db:backup -- <new archive>` and `npm run db:restore -- <archive> vocabularium_restore_stage4_20260923` succeeded. The restored database was separate from development. The application verified the restored default-deck relationship, two layout pages, empty card set, and account login. The restore database is retained for inspection. The archive contains the fresh seed; a populated-account restore and machine-restart rehearsal remain part of Stage 7.

A controlled integration test terminated the dedicated PostgreSQL ownership connection during a pending provider call. The completed result reached the filesystem journal while the database write failed. Restart recovered that exact result, and explicit publication succeeded without another model invocation. The test also completed an independent account write while the provider was waiting, verifying that provider work does not occupy the account executor/transaction.
